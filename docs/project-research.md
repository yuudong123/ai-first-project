# 프로젝트 기획 및 조사

- 작성일: 2026-08-28
- 가제: **HydroTwin — 멀티센서 기반 유압 시스템 부품 상태 조기예측 및 원인 분석 3D 디지털 트윈**
- 데이터: [UCI Condition Monitoring of Hydraulic Systems](https://archive.ics.uci.edu/dataset/447/condition+monitoring+of+hydraulic+systems)

## 0. 프로젝트 한 문장 정의

유압 설비의 압력·유량·온도·진동·모터 전력 데이터를 분석하여 **냉각기, 밸브, 펌프, 축압기의 상태와 심각도를 운전 초기에 판별**하고, 이상 부품과 판단 근거를 Unity WebGL 3D 화면에서 직관적으로 보여주는 설비 상태 모니터링 서비스다.

## 1. 프로젝트 효과 조사

### 1.1 해결하려는 문제

유압 설비는 여러 부품과 센서가 연결되어 있어 단일 임계치나 한 개 그래프만으로 문제 부품을 찾기 어렵다. 이상을 발견하더라도 압력, 유량, 온도, 진동 등 여러 신호를 따로 확인해야 하므로 비숙련자는 판단하기 어렵고 조치가 늦어진다.

### 1.2 As-Is / To-Be

| 구분 | As-Is | To-Be |
|---|---|---|
| 상태 판단 | 작업자가 여러 센서 그래프와 임계치를 개별 확인 | AI가 4개 주요 부품의 상태와 심각도를 동시에 판별 |
| 이상 위치 | 경보 발생 후 문제 부품을 수동 탐색 | 3D 설비에서 이상 부품을 색상과 애니메이션으로 즉시 표시 |
| 판단 근거 | 경보 수치만 제시되어 원인 추적이 어려움 | SHAP 등으로 판단에 크게 기여한 센서와 변화 방향 제시 |
| 대응 방식 | 고장 후 대응 또는 일정 기반 점검 | 위험도 기반 우선 점검 및 조치 권고 |
| 배포·운영 | 모델과 서비스가 수동으로 교체됨 | 테스트, 성능 검증, 컨테이너 배포를 Jenkins 파이프라인으로 자동화 |

### 1.3 참고 사례

1. **Siemens Senseye**: 글로벌 자동차 제조사의 1만 대 이상 설비를 모니터링하여 문제를 수개월 전에 식별하고, 불필요한 정비와 다운타임을 줄인 사례다. 이 사례는 멀티 설비 상태 모니터링의 사업 효과를 설명하는 참고 근거로 사용한다.  
   출처: [Siemens predictive maintenance case study](https://resources.sw.siemens.com/en-US/brochure-senseye-predictive-maintenance-increases-oee/)
2. **Toray Plastics / TwinThread**: 공정 이상을 탐지하고 문제의 근본 원인 후보를 찾도록 지원하여 필름 파손과 라인 불안정을 줄인 사례다. 우리 프로젝트의 `이상 탐지 → 영향 센서 분석 → 조치` 흐름과 유사하다.  
   출처: [Microsoft TwinThread case study](https://partner.microsoft.com/en-US/case-studies/twinthreadtoray)
3. **Yara 디지털 트윈**: 분산된 설비 정보를 3D 맥락 안에서 탐색하게 하여 정지 후 문제 해결 시간을 단축한 사례다. Unity 3D 화면을 단순 장식이 아니라 설비 탐색 UI로 설계해야 하는 근거로 사용한다.  
   출처: [Microsoft Yara customer story](https://www.microsoft.com/en/customers/story/26373-yara-international-azure)

> 위 사례의 절감액이나 개선율은 해당 기업의 결과다. 우리 프로젝트의 효과로 그대로 주장하지 않고, 구현 후 측정할 KPI를 별도로 제시한다.

### 1.4 프로젝트 목표 KPI

| 영역 | 측정 지표 | 1차 목표 |
|---|---|---|
| 모델 | 부품별 Macro F1 | 베이스라인 구축 후 목표치 확정, 우선 0.85 이상을 도전 목표로 설정 |
| 조기판별 | 10/20/30/60초 입력별 성능 | 20초 모델이 60초 모델 성능의 95% 이상 유지하는지 검증 |
| 오경보 | 정상 상태의 고장 오분류율 | 부품별 혼동행렬로 측정하고 최소화 |
| API | CPU 추론 응답시간 | 전처리된 1개 사이클 기준 p95 500ms 이내 |
| UI | 이상 위치 확인 시간 | 사용성 테스트에서 10초 이내 목표 |
| 운영 | 코드 변경 후 검증·배포 | 테스트 통과 시 Jenkins가 Docker 이미지까지 자동 생성 |

목표 수치는 확정 성과가 아니라 프로젝트 검증 기준이다. 최종 발표에는 실제 측정 결과만 기록한다.

## 2. AI 분석 데이터 조사

### 2.1 데이터 개요

- 출처: UCI Machine Learning Repository
- 데이터 유형: 다변량 시계열
- 라이선스: CC BY 4.0
- 크기: 압축 파일 약 73.1MB, 2,205개 운전 사이클
- 사이클 길이: 각 60초
- 결측값: 없음
- 실험 장치: 오일 탱크로 연결된 주 작동 회로와 냉각·여과 보조 회로
- 원본 논문: Helwig, Pignanelli, Schütze, *Condition Monitoring of a Complex Hydraulic System Using Multivariate Statistics*, IEEE I2MTC 2015, DOI `10.1109/I2MTC.2015.7151267`

### 2.2 입력 센서

| 센서 그룹 | 수량 | 샘플링 주기 | 60초당 값 |
|---|---:|---:|---:|
| 압력 PS1~PS6 | 6 | 100Hz | 센서당 6,000개 |
| 모터 전력 EPS1 | 1 | 100Hz | 6,000개 |
| 유량 FS1~FS2 | 2 | 10Hz | 센서당 600개 |
| 온도 TS1~TS4 | 4 | 1Hz | 센서당 60개 |
| 진동 VS1 | 1 | 1Hz | 60개 |
| 냉각 효율 CE·냉각 출력 CP·효율계수 SE | 3 | 1Hz | 센서당 60개 |

서로 다른 물리량을 함께 사용하므로 **멀티센서·다중 물리량 데이터**라고 표현한다. 영상·음성까지 포함한 멀티모달 데이터는 아니다. Unity 3D 화면도 모델 입력이 아니므로 멀티모달의 근거로 세지 않는다.

### 2.3 예측 대상과 실제 분포

| 부품 | 상태 값 | 표본 수 |
|---|---|---|
| 냉각기 | 정상 100 / 효율 저하 20 / 고장 근접 3 | 741 / 732 / 732 |
| 밸브 | 정상 100 / 미세 지연 90 / 심각 지연 80 / 고장 근접 73 | 1,125 / 360 / 360 / 360 |
| 펌프 | 누설 없음 0 / 약한 누설 1 / 심각한 누설 2 | 1,221 / 492 / 492 |
| 축압기 | 정상 130 / 약한 저하 115 / 심각 저하 100 / 고장 근접 90 | 599 / 399 / 399 / 808 |
| 안정 상태 플래그 | 안정 0 / 아직 안정화되지 않음 1 | 1,449 / 756 |

### 2.4 이 프로젝트에 적합한 이유

- 제품 불량이 아니라 **설비를 구성하는 4개 부품의 상태**가 정답으로 제공된다.
- 압력, 유량, 전력, 온도, 진동 등 여러 물리 신호를 결합할 수 있다.
- 부품별 고장 심각도가 있어 단순 정상/비정상보다 풍부한 결과를 만들 수 있다.
- 데이터가 작아 저사양 교육장 PC에서도 통계 특징 기반 모델을 학습할 수 있다.
- 유압 회로와 부품의 공간적 관계가 명확해 Unity 3D 디지털 트윈과 연결하기 좋다.

### 2.5 반드시 공개할 한계

- 실제 현장에서 고장이 진행된 run-to-failure 이력이 아니라, 실험 장치에서 부품 상태를 조절해 측정한 데이터다.
- 미래의 고장 시점이나 잔여수명(RUL)을 직접 예측할 수 없다.
- 정답은 부품 상태이지 정비사가 확정한 근본 원인 보고서가 아니다.
- 따라서 `고장 N시간 전 예측`이나 `인과관계 증명`으로 발표하면 안 된다.

프로젝트에서 말하는 원인 분석은 다음 범위로 제한한다.

1. 어떤 부품이 어떤 상태로 판별되었는가
2. 어떤 센서 특징이 그 판단에 크게 기여했는가
3. 센서 변화가 유압 회로의 어느 위치와 연결되는가
4. 어떤 부품을 우선 점검해야 하는가

발표 표현은 **“운전 초기 센서 패턴 기반 부품 상태·고장 위험 조기판별 및 원인 후보 분석”**으로 통일한다.

### 2.6 분석 설계

1. 60초 전체 데이터로 기준 모델을 만든다.
2. 각 센서를 1초 단위 또는 통계 특징으로 변환한다.
3. 평균, 표준편차, 최솟값, 최댓값, 범위, 기울기, RMS와 필요한 주파수 특징을 추출한다.
4. 10초, 20초, 30초 입력 모델을 별도로 만들어 전체 60초 모델과 성능을 비교한다.
5. 냉각기·밸브·펌프·축압기 모델을 각각 학습한다.
6. 인접 사이클이 학습·검증에 섞여 성능이 부풀지 않도록 시간 순서 기반 분할도 함께 검증한다.
7. 안정 상태 플래그는 입력 특징으로 사용하지 않는다. 안정 상태 데이터로 기준 모델을 만들고, 미안정 데이터는 강건성 시험에 활용한다.
8. SHAP으로 부품별 상위 영향 센서와 특징을 반환한다.

## 3. 필요 기술 정의

### 3.1 전체 흐름

```text
UCI 원본 센서 TXT
  → 데이터 검증·전처리
  → 시계열 특징 추출
  → 부품별 상태 모델
  → FastAPI 예측 API
  → 웹 대시보드 + Unity WebGL 디지털 트윈
  → 모델·서비스 모니터링

Git push
  → Jenkins 테스트
  → 모델 성능 기준 확인
  → Docker 이미지 빌드
  → 배포 또는 이전 버전 유지
```

### 3.2 기술 스택과 범위

| 영역 | 기술 | 사용 목적 | 우선순위 |
|---|---|---|---|
| 협업 | Git, GitHub | 브랜치·PR·코드리뷰·버전관리 | 필수 |
| 데이터 | Python, pandas, NumPy, SciPy, Parquet | 원본 파싱, 특징 추출, 경량 저장 | 필수 |
| 모델 | scikit-learn, LightGBM 또는 RandomForest | 저사양 CPU 기반 다중 분류 | 필수 |
| 설명 | SHAP | 부품 상태 판단에 영향 준 센서 설명 | 필수 |
| API | FastAPI, Pydantic | 예측·상태·센서 스트리밍 API | 필수 |
| 웹 | HTML/CSS/JavaScript, Chart.js | 실시간 센서 차트와 상태 패널 | 필수 |
| 3D | Unity, WebGL | 설비·유량·고장 위치 시각화 | 필수 |
| 테스트 | pytest | 전처리·모델·API 회귀 테스트 | 필수 |
| 실행 환경 | Docker, Docker Compose | 팀 PC와 배포 환경 통일 | 필수 |
| CI/CD | Jenkinsfile | 테스트와 Docker 빌드 자동화 | 필수 |
| 모델 운영 | MLflow 로컬 저장소 | 실험, 지표, 모델 버전 관리 | 고도화 |
| 재학습 | 데이터 검증 + 성능 게이트 | 새 라벨 배치가 들어온 상황을 모의하여 재학습 | 고도화 |
| 저장소 | Parquet, JSONL, MLflow 파일 저장소 | DB 없이 데이터·로그·모델 저장 | 필수 |

정적 공개 데이터만 사용하므로 실제 신규 현장 데이터가 자동 유입되는 것은 아니다. 자동 재학습 데모는 보류 데이터를 신규 라벨 배치처럼 순차 투입하여 `검증 → 재학습 → 기존 모델 비교 → 기준 통과 시 승격` 과정을 재현한다.

### 3.3 Unity WebGL 화면 요구사항

- 오일 탱크 → 펌프 → 밸브 → 작동부 → 필터·냉각기 → 축압기 흐름을 단순한 저폴리 3D로 표현
- 정상/주의/경고/위험을 초록/노랑/주황/빨강으로 표시
- 펌프 누설, 밸브 동작 지연, 냉각 효율 저하, 축압기 압력 저하를 서로 다른 애니메이션으로 표현
- 부품 클릭 시 현재 상태, 신뢰도, 상위 영향 센서, 권장 점검 내용을 표시
- 원본 100Hz 데이터를 전부 그리지 않고, 서버에서 1초 단위로 집계하여 저사양 PC와 브라우저 부하를 줄임
- Unity는 FastAPI의 JSON 응답을 일정 주기로 조회하고, 웹 차트와 동일한 예측 결과를 사용

### 3.4 Git 운영 규칙

- `master`: 시연 가능한 안정 버전만 유지
- 작업 브랜치: `feat/data`, `feat/model`, `feat/api`, `feat/unity`, `feat/web`, `docs/presentation`
- 데이터 원본, 학습 산출물, Unity 빌드 결과는 Git에 직접 올리지 않음
- 작은 단위로 커밋하고 Pull Request에서 최소 1명이 확인한 뒤 병합
- API 요청·응답 형식은 문서로 먼저 합의하여 Unity와 백엔드가 동시에 개발 가능하게 함

### 협업 원칙

- 팀장은 공통 골격과 인터페이스를 만들고, 팀원에게 완료 기준이 작은 작업 단위로 전달한다.
- 팀원은 매일 실행 화면 또는 그래프처럼 확인 가능한 결과물을 남긴다.
- Unity 프로젝트는 팀장이 단독으로 수정하여 Scene·Prefab 병합 충돌을 방지한다.
- Unity는 실제 모델이 완성될 때까지 기다리지 않고 동일한 형식의 mock JSON으로 병렬 개발한다.
- 발표 자료는 마지막 날에 몰아서 만들지 않고 기능이 완성될 때마다 캡처와 설명을 저장한다.
